# Decision log - Personal Money and Expense Logging System

**Version:** v0.1 (baseline) - 2026-10-23
**Status values:** *Adopted* (applied in the baseline), *To confirm* (applied by default, to validate with the TA).
Any later change is recorded as a new line with the old decision marked *Superseded*; history is never rewritten.

| ID | Decision | Rationale | Alternatives rejected | Impacts | Status |
|---|---|---|---|---|---|
| D-01 | **Stack = TokTickIT stack:** Node.js + TypeScript server (Express-style middleware, Prisma ORM) and React client. | The master spec encourages reusing the Labs 1-4 stack; the team already has working auth, Supertest and UI foundations, so effort goes to the domain. | New stack (learning cost with no assessed benefit). | All | Adopted |
| D-02 | **Database:** keep the Prisma provider used in the labs; keep the schema portable (no provider-specific features) so Lab 5 can move to PostgreSQL on GCP if needed. Migrations and seed are versioned. | Persistent database with documented schema is mandatory; Docker/GCP packaging comes in Lab 5. | Provider-specific types or raw SQL. | NFR-07, SR-02 | Adopted |
| D-03 | **Authentication as in Lab 3:** email + password, bcryptjs cost 12, server-side `Session` table with httpOnly signed cookie, Role as a Prisma enum, `requireAuth` / `requireRole` middleware. The Lab 3 mandatory first-login password change is **not** carried over (keeps Sprint 1 small; spec does not require it). | Proven in Lab 3; server-side sessions give real logout invalidation. | JWT (no server-side revocation); argon2 (native build problems on Windows). | FR-01..04, NFR-01, NFR-02 | Adopted |
| D-04 | **Session lifetime:** 8 hours absolute. Logout deletes the session row; disabling a user deletes all of their sessions. | Simple, testable expiry; supports BR-17. | Sliding expiry (more cases to test in Sprint 1). | NFR-05, BR-17 | Adopted |
| D-05 | **Roles:** `USER` and `ADMINISTRATOR`. Financial endpoints require `USER`; user-management endpoints require `ADMINISTRATOR`. The administrator owns no accounts and receives 403 on every financial endpoint. Identity and role come only from the session. | Matches the theme's identity/access statement; hidden buttons are not authorization. | Administrator as a super-user; client-selected role. | FR-04, BR-16 | Adopted |
| D-06 | **Money = integer satang (minor units), THB only.** Stored as integer; API fields use integer minor units (e.g. `amountMinor`); formatting to `1,200.00` happens in the client. Per-transaction maximum 1,000,000,000 minor units. | Exact arithmetic (NFR-04); avoids floating point and decimal-type portability issues between database providers. | Floats; Decimal type (provider-dependent in Prisma). | BR-02, BR-15, NFR-04 | Adopted |
| D-07 | **Balances are derived** from recorded transactions (opening balances + transaction effects); no stored balance column in Sprint 1. | A stored balance can drift from the ledger; derivation keeps one source of truth and is easy to unit test. A cached column may be added later if NFR-11 requires it. | Stored running balance. | BR-06, FR-07, FR-08 | Adopted |
| D-08 | **Transaction model:** a transaction header (owner, kind `PAYMENT` / `RECEIPT` / `OPENING_BALANCE`, main account, date, total, description) with allocation lines (target account, amount, memo). Opening balances have no lines. | Mirrors the brief (one transaction, several allocation lines) and supports all later features without schema rewrites. | One row per line without header; separate tables per form. | BR-01, BR-03 | Adopted |
| D-09 | **Balance-effect table** (SRS 4.3): Cash balance = money held; Loan Taken balance = outstanding debt (a charge raises it, a repayment lowers it); Loan Given balance = amount owed to the user; Income and Expense accounts accumulate totals. | One consistent sign convention removes special cases and defines unit-test cells. | Signed balances where debts are negative. | BR-05, BR-06 | Adopted |
| D-10 | **Allocation matrix:** Payment targets = Expense, Loan Taken, Loan Given, Cash; Receipt targets = Income, Loan Given, Loan Taken, Cash. A target equal to the main account is rejected. The model and validator support every combination from day one; Sprint 1 exposes only Income, Expense and Loan Taken repayment in the UI. | Avoids per-combination special cases; later sprints add screens, not rules. | Restricting card payments to expenses only. | BR-03, BR-04 | Adopted |
| D-11 | **No overdraft and repayment cap:** a Cash account may not become negative, and a repayment may not exceed the outstanding amount. Both are checked on the resulting current balance, not on historical running balances of back-dated transactions. | Meaningful, testable business rejections; limits complexity. Limitation is documented. | Allow negative cash; historical re-validation. | BR-07, BR-08 | Adopted |
| D-12 | **Dates:** calendar date in Asia/Bangkok, not in the future, no time of day. | Matches how people record expenses; simple boundary tests (today accepted, tomorrow rejected). | Timestamps; time zones per user. | BR-09 | Adopted |
| D-13 | **Immutability in Sprint 1:** no edit or delete operation. Sprint 2 corrections void the original and link a replacement, keeping an audit trail. | Prevents silent history rewriting and keeps Sprint 1 small. | Direct edit and delete. | BR-19, FR-20 | Adopted |
| D-14 | **Opening balance** is a transaction of kind `OPENING_BALANCE` on one account (Cash, Loan Taken or Loan Given), at most one per account in Sprint 1, never counted as income or expense. Editing arrives in Sprint 3. | Satisfies "records an opening bank balance" while keeping balances derivable. | Opening balance as an editable account field. | BR-12, FR-11, FR-12 | Adopted |
| D-15 | **Error semantics:** 401 unauthenticated; 403 wrong role; **404 for another user's resource** (indistinguishable from a missing one); 400 malformed or schema-invalid input; 422 business-rule violation with a machine-readable `error.code`. Error body: `{ "error": { "code", "message", "details?" } }`, never a stack trace. | Avoids leaking existence of other users' data; distinguishes validation from rule rejections in tests. | 403 for foreign records (leaks existence). | BR-10, NFR-01, NFR-08 | Adopted |
| D-16 | **Identifiers and paging:** opaque string IDs (cuid). History is paginated with `page` and `pageSize` (default 20, maximum 100), newest first. | Non-guessable IDs; bounded responses. | Sequential integers. | FR-21, NFR-11 | Adopted |
| D-17 | **Seed data (synthetic):** two users `demo.user1@example.test`, `demo.user2@example.test` and one administrator `demo.admin@example.test`. Each user has Wallet and Main Bank Account (Cash), Credit Card (Loan Taken), one Loan Given account, Income accounts (Salary, Interest Earned) and Expense accounts (Dining, Groceries, Electricity, Telecom). Passwords come from the `SEED_PASSWORD` environment variable; the seed refuses to run without it. | Two users enable cross-user tests; no real password is committed (NFR-12). | Hard-coded passwords in the seed. | A-06, NFR-06, NFR-12 | Adopted |
| D-18 | **Sprint 1 slice = theme 7's example:** opening balance, salary into the bank, card purchase with two expense lines, partial card repayment from the bank, then balances, debt, summary and history. Accounts are seeded; account creation is Sprint 2. | Matches the minimum scope in the master spec. | Including account creation in Sprint 1. | Plan, Q-01 | To confirm |
| D-19 | **Documents are Markdown in `docs/`**; the Deliverable 1 PDF is built from them (Pandoc) with a table of contents and a navigation table. The PDF is a build artifact, never edited by hand. | One source of truth; no copy-paste divergence between repo and PDF. | Writing directly in Word. | Deliverables | Adopted |
| D-20 | **Git workflow:** `main` (releases only) <- `sprint-N-staging` <- `feature/<issue>-<slug>` and `fix/<issue>-<slug>`. Feature PRs target staging and use merge commits (no squash) so the red-to-green history stays visible. A reviewed release PR goes from staging to `main`, followed by a tag `v0.N.0-sprintN`. The author never approves their own PR. | Required by the master spec; preserves evidence for Parts E and F. | Squash merges; direct pushes to `main`. | Parts E, F | Adopted |
| D-21 | **TDD evidence:** for rule work, commit the failing test first (`test:` prefix, observed red), then the implementation (`feat:` / `fix:`), then record both commit IDs in the Issue. Contracts and STS are committed (`docs:`) before the code they govern. | Makes the specification-then-implementation sequence verifiable. | One combined commit. | Part E, F | Adopted |
| D-22 | **Test tooling:** Supertest for API tests and the test runner and E2E tool already used in Labs 1-3; coverage from the runner (ledger module target in NFR-09). Test names embed the AC ID. | Reuse; direct AC-to-test traceability. | Mock-only persistence tests (not accepted by the spec). | NFR-09 | Adopted |
| D-23 | **Validation at the API boundary** with a schema library (the one used in Labs 2-3 if any, otherwise Zod); business rules live in the ledger module, not in controllers or the UI. | One place for rules, testable without HTTP. | Rules duplicated in client and server. | BR-01..BR-09 | Adopted |
| D-24 | **Pair protocol:** both students author and review; no permanent roles. Alternate PR authors by Issue; pair sessions are recorded with `Co-authored-by` trailers and named in the Issue. A contribution table is kept in `docs/contributions.md`. | Required by the master spec section 2. | One student writes specs, the other code. | Part F | Adopted |
